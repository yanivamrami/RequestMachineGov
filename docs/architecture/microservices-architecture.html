Requests platform: microservices architecture

Part B. Five services, each owning its own database. Services call each other synchronously only when the caller needs the answer right away; everything else travels as events through the broker, using a transactional outbox and idempotent consumers. Hover over a box for its API, and pick a flow to highlight it. The full design is in microservices.md; data-flow.html animates the failure and retry scenarios.

Communication rules

  • One DB per service; no service reads another's tables
  • Sync REST only when the caller needs the answer now (validation, lookups)
  • Events for "this happened, react to it" (notifications, reporting)
  • Gateway validates the JWT; each service authorizes from the claims

Reliable notifications

  • Outbox: request change + event committed in one DB transaction; a relay publishes it
  • Durable queue per consumer: if Notifications is down, events wait
  • Idempotent consumers: dedupe on messageId; version drops stale events
  • Retry ladder: 3 immediate tries → redelivery 1m/5m/30m/2h → DLQ + alert

Sync resilience

  • Timeout per attempt + overall
  • Retry with backoff + jitter, only for idempotent calls
  • Circuit breaker: fail fast with 503 instead of piling up threads
  • Client Idempotency-Key on POST/PATCH
